# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

The parent `salt-formulas/CLAUDE.md` describes what every formula of the
collection shares: the toolchain (`bin/kitchen`, pre-commit), the `map.jinja`
merge chain, the `package/config/service` decomposition, TOFS and the CI. This
file only covers what is specific to `syslog-ng-formula`.

## Layout specifics

- The state tree is `syslog_ng/` (underscore, `top_level_dir` in `FORMULA`),
  the repo is `syslog-ng-formula/`. Pillar root key is `syslog_ng`.
- The formula manages exactly one file, `/etc/syslog-ng/syslog-ng.conf`,
  rendered from `syslog_ng/files/default/syslog-ng.conf` through
  `files_switch()` (TOFS lookup id `syslog_ng/config/install`).
- `syslog_ng/osfingermap.yaml` is the only map level that matters for Debian:
  per `osfinger` it sets `version` (the `@version:` line, matching the distro's
  syslog-ng package: `Debian-11` 3.28, `Debian-13` 4.8), `include` and
  `last_include`. `osarchmap.yaml`, `osmap.yaml` and `osfamilymap.yaml` carry
  nothing for Debian.

## How the pillar becomes `syslog-ng.conf`

The whole configuration language is generated by one recursive macro,
`rule_builder` in `syslog_ng/macro.jinja`. Its rules, by value type:

| Pillar value | Rendered as |
|---|---|
| `null` | nothing (so `internal: null` → `internal()`) |
| `true` / `false` | `yes` / `no` |
| number | bare number |
| string starting with `=` | the rest, verbatim (`=not level(debug)`, `=s_src`, `=0640`) |
| any other string | double-quoted (`/var/log/syslog` → `"/var/log/syslog"`) |
| mapping | `key(value)` for each key |
| list | each element rendered and concatenated, **no separator** |

The template (`files/default/syslog-ng.conf`) walks the top-level keys in a
fixed order: `version` (defaults to `3.3` if no map level sets it), `module`,
`include`, `options`, then `source`, `destination`, `filter`, `parser`,
`rewrite`, `template`, then `log`, then `last_include`. Any other top-level
key is ignored.

Shapes that follow from this, see `pillar.example` and the fuller Debian
layout in `pillar.debian.example`:

- `options` is a list of single-key mappings, one `key(value);` line each.
- Each object type is a list of `{name: [rules...]}` mappings, so declaration
  order is preserved.
- `log` is a list of lists: each inner list is one `log { ... };` block, and
  references to named objects must use the `=` prefix (`source: =s_src`)
  or they would be quoted.

## Config validation

`config/file.sls` sets `check_cmd: syslog-ng --syntax-only -f` with
`tmp_dir` pointing at the config's own directory: a rendering that syslog-ng
rejects never replaces the running file, and relative `@include "scl.conf"`
lines resolve as they will in place. `service/running.sls` restarts the
service through `watch` on the config SLS.

## Tests

One Kitchen suite, `default` (`bin/kitchen list` → 3 instances, one per
fleet platform).

- `test/salt/pillar/syslog_ng.sls` is the test pillar.
- `test/integration/default/controls/config_spec.rb` asserts that the
  rendered file **includes a literal multi-line block** (`source s_src`,
  `destination d_syslog`, `filter f_syslog3`, `log`). Whitespace and line
  breaks are significant: any change to the test pillar, to `rule_builder` or
  to the template's indentation must be carried into that string.
- This fork has no `_mapdata` reference dumps under
  `test/integration/default/files/`: the `_mapdata` state still runs in the
  suite's `state_top`, but nothing compares its output.
